# Came back: returned, then re-dispatched — implementation plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** When a delivery comes back undelivered (a stop failed: closed, refused, damaged, wrong address), Simple TMS tells Simple WMS it came back; Simple WMS puts it back on its ledger at a returns dock, through the task engine, and fires `delivery.returned`; when it goes out again, on a run or with a carrier, Simple WMS ships it again with the new run number or con note and fires `delivery.shipped` again.

**Architecture:** Simple WMS gains `POST /v1/deliveries/{ref}/return`, a `returns` zone kind, a `returned` delivery status and a `return` task type: the call raises a return task with a line per carton line and confirms it at once, and confirming a line writes one `return` ledger row into the first location of the warehouse's returns zone (batch, carton, owner and the shelf's received date kept). Shipping a `returned` delivery takes the stock out of that dock instead of the packing bench. Simple TMS queues a return call for each failed stop when the run is finished (the truck is back), through the existing `outbound_call` queue, which now makes a consignment's calls strictly in order; a failed consignment can be planned at once but can't leave again until its run is finished.

**Tech Stack:** Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2, Alembic, pytest on a real PostgreSQL 16 (both APIs); Vite, React 19, TypeScript, Vitest with Testing Library (both desktops); Docker Compose and Caddy for the manual check. No new dependencies.

### 1. The rules, and how each is kept

Simple WMS (`CLAUDE.md`):

- **The stock ledger is append-only.** Coming back is new `return` rows (positive, into the returns dock); going again is new `ship` rows out of the dock. Nothing is updated. The ledger invariant (balances rebuild from the ledger) is checked in the new tests.
- **Everything is a task.** The return is a `return` task with a line per carton line, raised by the call and confirmed by it through `tasks.confirm`, which is the only place the return rows are written (`_confirm_return`); the delivery's status follows the task's completion hook, as a pick's does. No special-case path writes the ledger. (Shipping itself is unchanged: it was never its own task and hangs off the pack task, so shipping again does too.) A cancelled delivery that came back gets an ordinary put-away task off the dock.
- **Decimals with a UoM.** Quantities come from the package lines (`Qty`, with their `uom`); events carry decimal strings.
- **The API is the only door; every endpoint in `docs/api.md`.** One new endpoint, documented in Task 9 with its errors, the new status, zone kind, task type, event, and what SAP does (and doesn't) with it.
- **Git:** subject line and, if needed, a short body; no `Co-Authored-By`, no tooling or generated-by trailers, no session links. Australian English.

Simple TMS (`CLAUDE.md`):

- **History is append-only.** A new `returned` history row; the consignment's `status` stays `failed`.
- **A delivery is recorded once.** Each return call has its own `message_id`, queued in the same transaction as the finish (which is itself once per `message_id`); finishing a finished run queues nothing. Simple WMS answers a repeated `message_id` with its first reply, and `409 already_returned` is taken as done.
- **The API is the only door.** No new endpoint; `GET /v1/runs/{id}` gains `returns`, the manifest loses `already_shipped`, and two `409 not_back`s are added; all in `docs/api.md` (Task 17).
- `CLAUDE.md` says "Nothing in Simple WMS changes for it." That stops being true; Task 17 changes the line (Decision 17).

### 2. The code as it is on `main`

Simple WMS:

- **Ship** (`api/wms/services/outbound.py` `ship`, route `POST /v1/deliveries/{ref}/ship` in `api/wms/api/routes/outbound.py`): refuses `already_shipped`, `cancelled`, `not_packed`, `short_not_allowed`; writes one `ship` row per package line out of `delivery.staging_location_id` (the packing bench), `task_id` the pack task; sets `carrier`, `tracking_no`, `status = "shipped"`; emits `delivery.shipped` (`delivery_ref, carrier, tracking_no, short, lines[qty_ordered, qty_shipped], packages`). Statuses: `new, allocated, picking, picked, packing, packed, shipped, cancelled`. `cancel` refuses a shipped delivery and raises a put-away task for stock left on the bench.

Transfers' in-transit bucket is "the first location of an `in_transit` zone", and a warehouse without one is a `422` naming what to add: the pattern the returns dock follows.
- **Events** (`services/events.py`): `emit` queues one row per matching subscriber (`*`, `x.*` or exact names) inside the caller's transaction. Inbound idempotency is `envelope.handle` on `message_id`, 24 hours.
- **SAP** (`services/sap.py`): each mapped event is one `BAPI_GOODSMVT_CREATE`; `delivery.shipped` is `GM_CODE 03`, movement `601`; an unmapped event fails at once (`Unmapped`). `settings.movement_types` and `settings.gm_codes` override per subscriber. `routes/integration.check_transport` validates an `sap_rfc` subscriber.

- **Local data** (read only): subscribers `ERP bridge` (http, `delivery.shipped, stock.adjusted, transfer.*, production.*`, active), `sap-erp` (sap_rfc, `receipt.confirmed, stock.adjusted`, inactive), `simple-tms` (`delivery.*`). `BAL-WH01` has no returns zone (nor an in-transit one). The demo seed (`wms/demo.py`) has none either; Task 7 adds one.

- **Fail** (`api/tms/services/deliveries.py` `fail`): the stop's outcome and the consignment become `failed`, history `failed` with the reason; it is back in the tray (`PLANNABLE` and carriers' `BOOKABLE` include `failed`) and can go on another run or with a carrier at once.
- **Finish** (`deliveries.finish`): a departed run with every stop done becomes `done`; finishing a finished run returns it as it is. The driver's Finish and the office's **Finish run** both call it.

### Decisions

Settled with the user on 15 October 2026: the core flow as proposed (Decisions 1–9 and 12–19), the settled documents updated as proposed (17), `delivery.returned` added to the local ERP bridge (11), and **SAP left out of returns for now** (10, changed from this plan's first proposal). The **(you choose)** marks show where there were real alternatives.

1. **When Simple TMS tells Simple WMS: when the run is finished. (you choose)** The cartons are on the truck until it is back at the depot; "Finish" (the driver's, or the office's **Finish run**) is the one moment Simple TMS knows that. Telling Simple WMS at the driver's **Can't deliver** would put the stock on the returns dock's ledger hours before it is there, and a consignment could be "returned" and shipped again while still in the back of the first truck. So the return calls are queued by `finish`, one per failed stop, in its transaction. **Recommendation:** at finish. The other way (at the fail) is simpler and drops Decision 12, at the cost of the ledger running ahead of the stock.
2. **The return is a `return` task, raised and confirmed by the API call. (you choose)** The least special-case way that keeps "everything is a task": the same engine creates it (a line per carton line, `to_location` the dock), confirms each line (`tasks.confirm` → `_confirm_return` → `ledger.post`), and its completion hook makes the delivery `returned` and emits the event, as a pick task's hook makes a delivery `picked`. It is born and done in one transaction, as a `move` from `POST /v1/moves` is. A receive-like task was rejected: `receive` emits `receipt.confirmed` per line, which an ERP (and SAP, `101`) would post as a purchase receipt. **Recommendation:** as here. The alternative, an expected-return task the scanner confirms at the dock, is truer to the floor but holds the re-ship until someone scans it (Simple TMS's ship call would get `409` and back off) and needs a scanner screen; it can be added later by leaving the task `waiting` instead of confirming it in the call.
3. **The whole delivery comes back. (you choose)** Every package, every line, as shipped. Simple TMS has no part delivery: a delivery names every package. The endpoint takes no `packages` list, so a part return can be added later without breaking callers. **Recommendation:** whole only, for now.
4. **It waits in a returns zone, which each warehouse must have.** A new zone kind `returns`; the dock is the first active location in it (by pick sequence, then code), as the in-transit bucket is. No returns zone: `422` on `warehouse`, "BAL-WH01 has no returns zone for deliveries that come back; add one on the Locations screen", nothing written; Simple TMS's call backs off and shows that reason beside **Try again**. Stock there is on hand but never promised and never a put-away suggestion (it is that delivery's). The demo seed gets `RETURNS` / `RETURNS-01` in Ballarat and `RETURNS` / `MEL-RETURNS-01` in Melbourne; the Locations screen offers the kind. No migration creates zones in existing warehouses: Task 19 adds one to the local `BAL-WH01`, and a real site adds its own before deploying. (Falling back to the packing bench was rejected: it would mix stock waiting to go again with stock being packed.)
5. **The status machine: `shipped` → `returned` → `shipped` …, as often as it happens.** `POST …/return` needs `shipped` (`409 not_shipped`; `409 already_returned` if it came back and hasn't gone again). `POST …/ship` takes `packed` or `returned`. `POST …/pack` refuses a `returned` delivery (`409 not_open`): it goes again in the cartons it came back in. `POST …/cancel` now also takes a `returned` delivery: it becomes `cancelled`, `delivery.cancelled` fires, and a high-priority put-away task takes the stock off the dock (before this plan a cancel of a shipped delivery was refused, and that stays). `returned_at` and `return_location_id` (migration `0017`) record the last return.
6. **Going again ships out of the dock, with the new carrier and tracking number.** Same cartons, same ledger shape (a `ship` row per package line), `delivery.shipped` again with the same data shape as the first. No new field on `delivery.shipped`: a listener knows it is a re-shipment because `delivery.returned` came between.
7. **The received date travels with it.** The return rows carry the received date the stock had on the shelf it was picked from (the delivery's `pick` rows), so a cancel that puts it back on a shelf doesn't make old stock look new. Owner, batch and carton (`container_id`) are kept from the package lines.
8. **A return names the shipment that came back.** `tracking_no` in the body, when given, must be the delivery's current one, or `409 not_that_shipment`: a late word about an earlier trip can never bring back the one on the road now. Simple TMS always sends it (the run number).
9. **The `delivery.returned` event:** `{ delivery_ref, carrier, tracking_no, reason, note, location, returned_by, lines: [{ delivery_line, sku, batch, qty_ordered, qty_returned, uom }], packages: [{ package_no, weight_kg, sscc }] }`. `reason` is free text up to 64 characters (Simple TMS sends its four: `closed`, `refused`, `damaged`, `wrong_address`). It is a new event type: subscribers pick types by name, so only those on `*` or `delivery.*` get it unasked.
10. **SAP: returns aren't posted yet. (the user's choice)** The `sap_rfc` transport takes `delivery.returned` and posts nothing: the worker marks the event `delivered`, with "not posted to SAP: returns aren't posted to SAP yet; …" as its note, without dialling SAP. That is *not* how the transport treats events it doesn't map: those raise `Unmapped` and are marked `failed` at once (no retries), for a subscription that is a mistake. A return is expected and leaving it out is a choice, so it mustn't show red on the Integrations page every time a delivery comes back. The consequence, said plainly in `docs/api.md` (SAP), the README and the brief: a delivery that comes back and ships again reaches SAP as a **second goods issue (`601`) with nothing in between**, so SAP's stock is one shipment short for each such delivery until someone puts it right there. Whoever looks after SAP should map returns (a `653`-style receipt, say) before relying on SAP's stock for deliveries that come back. No mapping, no `GM_CODE`, and no check on SAP subscribers' event types are added. The first proposal (post `653` / `GM_CODE 05`, and refuse an SAP subscriber that hears `delivery.shipped` but not `delivery.returned`) is what "map returns" would be later. The local `sap-erp` is inactive and doesn't hear deliveries, so nothing changes there today.
11. **The ERP bridge hears `delivery.returned`. (confirmed)** The local `ERP bridge` subscriber hears `delivery.shipped` by name, so without this it would hear a delivery ship twice without hearing it came back. An http listener chooses for itself, so Simple WMS doesn't force it; Task 19 Step 3 adds `delivery.returned` to it (an update by name changes only the event types). Whatever is behind it has to answer `2xx` to it (ignoring it is fine), or Simple WMS retries it and marks it failed after the 2 h try.
12. **A failed consignment can be planned at once, but leaves again only once its run is finished.** Departing a run (the office's **Leaves now**, or the driver's **Start**) or collecting a manifest with such a consignment on it is `409 not_back`: "Station Deli (0080034519) is still on R-0007: finish that run once the truck is back, then this one can leave" (or "… then the carrier can take it"). Step 3's "plan tomorrow during today" still works. This follows from Decision 1: the return call has to exist before the next ship call.
13. **A consignment's calls to Simple WMS go strictly in order.** The worker claims a call only when no earlier call of the same consignment is still pending or has given up; a call that gave up holds the later ones (untried, not burning tries) until **Try again**. So Simple WMS hears shipped → returned → shipped in that order however the retries fall, which `already_shipped` can no longer paper over.
14. **`already_shipped` stays an answer, and the manifest's list goes.** Simple WMS now takes the re-shipment, so the step-6 path ("already shipped by its run") can't happen for anything that came back after this deploys. `409 already_shipped` and the new `409 already_returned` remain "done" for one reason: a reply lost past Simple WMS's 24 hours of remembering a `message_id` (with calls in order, that can only be the call's own work). The manifest's `already_shipped` list, the desktop's wording for it, the confirm's "unless its run already shipped it" and the README limitation go. The `outbound_call.already_shipped` column stays (it records how Simple WMS answered; dropping it would be a migration for nothing). Consignments that failed before the deploy have no return call and get `already_shipped` when they go again, as today, only now without the explanation on Carriers; the local data is to be reset, so none should be left.
15. **A run says what it handed back.** `GET /v1/runs/{id}` gains `returns` (`{ pending, done, failed, last_error }`, like `shipping`), and `shipping` counts ship calls only. **Plan runs** says "Back in Simple WMS: 1 of 1." on a finished run with returns, and "1 not marked back in Simple WMS after five tries: <why>" with **Try again** (`retry-ship`, which now restarts ship and return calls alike).
16. **History says it is back.** A `returned` row (`{ run, run_id, by }`) when the run is finished; the Consignments drawer shows it as "Back at the depot", with "off R-0007 · Simple WMS told · kim" under it. The status stays `failed`, so the tray, the map's **To plan** and the filters don't change.
17. **The settled documents change, with your say-so.** Simple TMS's `CLAUDE.md` ("Nothing in Simple WMS changes for it") and its design doc ("nothing in the WMS changes") are rewritten in Task 17; Simple WMS's `CLAUDE.md` rule 2 and `docs/brief.md` principle 2 gain "return" in their lists, and the brief gains a "Came back" feature line (Task 9). These are the documents that say "change them here first": skip those hunks if you'd rather word them yourself.
18. **What carriers bring back is still not recorded.** A carrier that returns freight has no step in Simple TMS; it stays `collected`. Simple WMS could take it back (`POST …/return` with the con note), but Simple TMS doesn't call it for a carrier. The README keeps that limitation, reworded.
19. **Deploy Simple WMS first.** A return call to a Simple WMS without the endpoint gets `404`, which backs off and gives up after the 2 h try; **Try again** mends it once Simple WMS is updated, but it is better not to need it.

**Still open:** none for this plan. Later: SAP's mapping for returns (10), a scanner step at the returns dock (2), part returns (3).

from wms.models import Location, OutboundEvent, StockBalance, StockLedger, Subscriber, Task, Zone
from wms.services.ledger import LedgerLine, post, rebuild_balances

def on_hand(db, location):
    return sum((b.on_hand for b in db.execute(
        select(StockBalance).where(StockBalance.location_id == location.id)).scalars()), Decimal(0))
